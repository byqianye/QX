## 2026-09-08 进展

已修复并验证：

- Rust 播放代理的大 HLS 清单使用 `Content-Length` 完整发送，并在发送后等待有界的客户端关闭；`playback_proxy` 相关测试 19 通过、2 个网络测试忽略。
- 播放恢复只在 `first-frame` 后标记成功；重复错误合并到同一个恢复工作，解析失败可在原 45 秒预算内继续候选；旧播放器停止和迟到同步不能覆盖新会话。
- 多源搜索保留逐源进度和来源归属；详情操作不会取消正在产生结果的搜索。
- 普通媒体代理允许一次同源重定向；跨源、多次跳转、私网和带凭据目标仍拒绝。
- 播放请求失败后明确落到 `error` 状态并释放播放器占位，避免界面停留在“正在加载”而无法重试或切换线路。
- 播放启动的剩余超时从 renderer 传入 `backend_playback_start`，再传入 Rust source `player` 调用，修复调用级超时没有覆盖后端会话的问题。
- Tauri CDP 验收脚本不再用额外 `video.play()` 掩盖产品起播问题，失败会保存 JSON 和截图，并先执行自定义关闭按钮。

当前真实源证据仍不足以建立稳定组。2026-09-08 Rust 测量显示肥猫搜索/详情可返回媒体地址；原先的普通重定向拒绝已修复为有限同源跟随，但新的真实 Tauri 短测仍在详情/播放状态切换期间超时，尚未产生解码帧。肥猫《凡人修仙传》清单完整到达但分片上游 `404`，没有解码帧。光盘首页有内容但海报加载验收未通过；干饭返回滑块挑战，方舟返回 `403`，番薯连接超时，蔬菜详情响应失败。当前没有任何源完成电影和剧集各 10 分钟连续解码，因此禁止标记本 Goal 完成或生成验收安装包。

同日全目录链路测量（`artifacts/g130-all-source-chain-0908.json`）发现少量 Bili 类来源能返回直接媒体地址，但它们共享 `csp_Bili` 后端，不能计作多个独立源；其它候选仍分别受到动态播放器、鉴权、超时或上游错误限制。该测量只证明接口链路，不证明视频解码。

## 2026-09-08 外部建议对照与补充复测

参考公开 CatVod/TVBox/DRPY 项目的生命周期和字段约定后，确认本项目应继续采用“声明式 JSON HTTP + 白名单 HTML + 专用 Rust 协议”三层边界；外部源清单只用于候选发现，不能替代真实播放器验收。当前新增的验收脚本支持自动首页模式下按内部站点 key 切源，来源卡片增加 `data-site-key` 测试标识。

补充复测结果：

- `荐片`（`csp_Jianpian`）：一次真实 Tauri 搜索→详情→播放短测解码 20 秒，首帧约 11.3 秒；后续同源搜索出现上游超时，因此记为“适配正确、偶发可播”，不记为稳定源。
- `蔬菜`（`csp_AppGet`）：搜索、详情和播放解析完成，但媒体清单/直链由上游返回 403，记为“适配正确、当前不可播”。
- `MTV`（共享 `csp_Bili` 后端）：自动切源初始化不稳定，未进入播放验收。

按用户要求的实际尺度，临时上游错误不会驱动无依据的协议扩展；仍保留三独立稳定源和十分钟连续播放作为 G130 的正式门槛。
