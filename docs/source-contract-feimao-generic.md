# 肥猫源通用性适配指南

状态：适配规范与问题清单（2026-09-08）

适用源：`http://xn--z7x900a.net/` 配置中登记的站点，以及同类 TVBox/CatVod 风格源。

## 目标

肥猫配置包含多个不同协议、不同运行时和不同可靠性的源。通用适配的目标是复用一套安全的 Rust 请求与结果转换流程，同时保留特殊源的专用边界：

1. 能识别配置并建立 SourceSession；
2. 能分别验证 `home`、`category`、`search`、`detail`、`player/playback`；
3. 能拿到明确的媒体地址；
4. 最终以真实 `<video>` 解码帧和持续播放作为可播放结论。

前两项只证明接口链路，第三项只证明媒体解析结果，均不能替代真实播放验收。

## 适配分层

### A. 声明式 HTTP 转换器

适用于普通 JSON HTTP 接口。配置使用 `qxAdapterVersion: 1`，描述：

- `baseUrl`
- 每个操作的 HTTP `method`、相对 `path`
- `query`、`headers`、JSON `body` 模板
- `response.root`、`fields` 和 `list.item` 的 JSON Pointer 映射

模板参数来自当前会话，例如 `{key}`、`{page}`、`{ids}`、`{id}`、`{flag}` 和 `{episode}`。路径只能是相对路径，不能借模板跳转到其他主机。

字段映射支持以 `?` 结尾的可选 JSON Pointer，例如 `/cover?`。字段缺失时跳过该字段；列表根路径、播放地址和其他必需字段仍然严格失败。

### B. 受控 HTTP 探测

没有完整声明式合同、但明确提供 CMS 地址的源，可以进入 `auto_http`。探测范围固定且有界，只接受可解析的 CMS JSON/XML，不执行远程脚本，不从 HTML 猜测播放地址。

探测成功只标记为 `http-auto`，不能直接标记为稳定可播。

### C. 专用 Rust 适配器

出现以下任一情况时停止扩展 JSON 转换器，改用专用适配器：

- AES、MD5、WBI 或其他动态签名；
- 加密响应或多阶段 discovery；
- HTML/iframe/脚本中的媒体提取；
- 登录态、验证码、滑块或设备指纹；
- 需要固定请求头、重定向或特殊播放代理；
- 播放地址必须经过源专用解析接口换取。

专用适配器必须保持请求超时、取消、响应大小和 URL 安全校验，不能通过“猜接口”扩大兼容性声明。

## 肥猫适配中确认的问题

| 问题 | 现象 | 处理边界 |
| --- | --- | --- |
| 配置可导入但源不可用 | 能读取 39 项配置，实际请求失败 | 配置识别与线上可用分开记录 |
| 非统一 JSON | 同一字段在 `data/list/result` 或不同别名下出现 | 使用显式 JSON Pointer；非关键字段用可选映射 |
| AppGet/AppQi 加密协议 | 固定 AES key/IV、POST 表单、一次性 discovery | 走专用 Rust 合同；缺 key 不伪装成声明式源 |
| 动态签名或脚本 | 需要 WBI、JS、DEX/JAR 或设备参数 | 不由转换器执行；保留专用运行时边界 |
| HTML/iframe 播放页 | 详情可见，播放页才暴露媒体地址 | 使用白名单 HTML 适配器，明确区分页面交接和媒体直链 |
| 重定向 | 媒体清单跳转到同源 CDN 或跨源地址 | 仅允许一次安全同源跳转；跨源、多次跳转、凭据和私网目标拒绝 |
| 清单或分片失败 | m3u8 可读取但分片 `404`、`403` 或超时 | 只能记录为媒体链路失败，不能算播放通过 |
| 播放卡在加载 | 后端 source 调用未继承 renderer 剩余超时 | 每次调用传递绝对剩余期限，取消和关闭必须释放会话 |
| 滑块、WAF、登录 | 返回挑战页或 `403` | 原样报告失败，不绕过验证 |
| 同后端多名称 | 多个条目实际共享 `csp_Bili` 等后端 | 稳定源统计按后端身份去重 |

已确认的肥猫样本：

- `光盘`：首页较快且有内容；媒体/CDN 稳定性仍需真实解码验证。
- `肥猫`：搜索、详情和部分清单可返回；部分分片返回 `404`，不能算稳定播放。
- `干饭`：返回 `APPQI_CHALLENGE_REQUIRED`。
- `方舟`：返回 `403`。
- `番薯`：连接超时。
- `蔬菜`：搜索可返回，详情失败。
- 若干 Bili 类条目：能返回直链，但共享同一后端，不能重复计数。

## 新源接入流程

1. 保存真实请求和响应样本，至少覆盖读取、搜索、详情、线路/选集和播放解析。
2. 先判断协议类型：普通 JSON、固定加密协议、HTML 播放页、动态脚本或挑战验证。
3. 普通 JSON 源先写声明式合同，只映射真实存在的字段；不要为缺失字段生成默认播放地址。
4. 运行 `npm run test:source-contract` 和 Rust `source_converter` 测试。
5. 使用真实源 canary 分别记录每个阶段的状态、耗时、响应大小和错误码。
6. 取得明确媒体地址后，再通过 Tauri 播放器验证首帧、解码时间、缓冲和连续播放。
7. 只有搜索、详情、媒体解析和实际解码都通过，才把源登记为稳定源。

## 验收记录格式

每个源至少记录：

- 源名称、`api`、实际后端身份；
- 协议层和适配器名称；
- `home/search/detail/player` 的状态与耗时；
- 媒体 URL 类型（MP4/HLS）、请求头和重定向次数；
- 首帧时间、观察时长、缓冲次数及每次持续时间；
- 失败阶段、错误码和网络环境。

“配置能导入”“接口返回列表”“`parse=0`”只能作为阶段性证据，不能写成“源已可用”。

## 当前结论

肥猫配置适合采用“声明式 HTTP 转换器 + 少量专用 Rust 适配器”的组合。转换器负责稳定、透明、可测试的 JSON 胶水；加密、动态签名、HTML 播放页和挑战验证必须维持隔离实现。当前尚未形成满足电影、剧集和连续播放门槛的三源稳定组，因此本文件是适配规范和问题基线，不是线上可用性承诺。

## 外部实现可借鉴的做法

公开的 CatVodSpider 类项目普遍把源实现围绕统一的 `homeContent`、`categoryContent`、`searchContent`、`detailContent` 和 `playerContent` 生命周期组织，这与本项目的 SourceSession 五阶段合同一致；可借鉴其阶段划分，不能直接把 Android/JVM Spider 当作 Rust 运行时使用。

公开的 TVBox 源聚合项目还展示了一种有价值的验收思路：先获取视频、下载 HLS 主清单和媒体清单，再下载首个分片并测量速度；不可用源自动清洗，恢复后再加入候选。该流程适合改造成项目内的离线基准，但最终仍需 Tauri `<video>` 解码帧和持续播放验收。

外部配置仓库通常只是源清单或订阅样例，不能作为源稳定性证明；配置内容会变化，也可能包含未经验证的第三方地址。因此本项目只把它们当作候选发现渠道，所有进入默认源或稳定组的条目仍必须通过本文件规定的逐阶段合同和真实播放测试。

### 外部建议落地尺度（2026-09-08）

外部项目提供的是协议形状和调试习惯，不是对上游站点可用性的承诺。对肥猫这类混合配置，建议把结果分成三层：

1. **适配正确**：请求方法、路径、参数、响应映射和播放字段均有真实样本；
2. **当前可用**：本次网络条件下完成搜索、详情、播放解析和媒体探测；
3. **稳定可播**：在真实 Tauri 播放器中起帧并连续观察达到项目门槛。

某个源出现临时 `403`、`404`、WAF 挑战、DNS 或连接超时，不应反向修改已经符合真实合同的 Rust 适配器，也不应把一次成功提升为长期稳定。每次重新搜索都应重新尝试候选，并记录最近一次失败阶段和时间。

外部规则源中的 `lazy`、`header`、`playUrl` 等字段可以映射为受控的播放解析结果和请求头；不得因此引入远程脚本执行、DEX/JAR 运行时或未验证的解析器。安装包继续只包含当前 Rust 适配层和播放器所需组件。
